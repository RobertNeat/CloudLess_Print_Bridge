CloudLess Print Bridge

Setup options

There are three ways to get the whole stack (the octo-management-dashboard plus its three backends — mqtt-puppeteer, ftps-remote-manager, and video-service-hub) running, in increasing order of permanence:

  • Development environment — for making code changes; each service runs from source with hot reload.
  • Docker Desktop — for trying the built stack locally, on your own machine, without a Node/Angular dev toolchain.
  • Local server — for a permanent, always-on installation on a LAN machine that the whole household/network can reach.

Development environment

This is the setup for actively working on the code: every service runs from source, with hot reload, under pnpm.

Install

pnpm install

Run each service in its own terminal

Each of the four apps needs its own terminal window/tab. Root scripts (from the repo's package.json): 

pnpm dev:mqtt        # @cloudless/mqtt-puppeteer      -> start:dev, :10320
pnpm dev:ftps        # @cloudless/ftps-remote-manager  -> start:dev, :10321
pnpm dev:video       # @cloudless/video-service-hub    -> start:dev, :10322 (+ MQTT :1883)
pnpm dev:dashboard   # @cloudless/octo-management-dashboard -> start (ng serve), :10300

Equivalent direct form, if you prefer --filter explicitly:

pnpm --filter @cloudless/mqtt-puppeteer start:dev
pnpm --filter @cloudless/ftps-remote-manager start:dev
pnpm --filter @cloudless/video-service-hub start:dev
pnpm --filter @cloudless/octo-management-dashboard start

Dev-server proxy

The dashboard's Angular dev server (ng serve, port 10300) proxies API calls to the three backends via apps/octo-management-dashboard/proxy.conf.json:

Path prefixProxies to
/api/mqtthttp://localhost:10320 (mqtt-puppeteer)
/api/ftpshttp://localhost:10321 (ftps-remote-manager)
/api/videohttp://localhost:10322 (video-service-hub)

The video-service-hub proxy target is hardcoded to port 10322 in proxy.conf.json. Running that service on a custom port breaks the dashboard's dev proxy for /api/video unless you also edit proxy.conf.json to match — the dev server does not auto-detect a different port. This is why the default pnpm --filter @cloudless/video-service-hub start:dev command (not a custom-port variant) is the one to use.

Environment variables

Copy the root .env.example to .env and fill in your printer's specifics — at minimum BAMBULAB_A1_IP, BAMBULAB_A1_ACCESS_CODE, and BAMBULAB_A1_SN (the printer's LAN IP, access code, and serial number, all found on the printer itself): 

cp .env.example .env

Key variables to fill in

  • BAMBULAB_A1_IP — printer's LAN IP address
  • BAMBULAB_A1_ACCESS_CODE — printer's access code
  • BAMBULAB_A1_SN — printer's serial number

Already set to sane defaults

  • MQTT_PUPPETEER_PORT=10320
  • FTPS_REMOTE_MANAGER_PORT=10321
  • VIDEO_SERVICE_HUB_PORT=10322
  • CLOUDLESS_AUTH_MODE=disabled

Build, test, lint

pnpm build                          # pnpm -r build (root script)
pnpm test                           # pnpm -r test (root script)
pnpm lint                           # pnpm -r lint (root script)
pnpm --filter <package-name> check  # lint + typecheck for one app

pnpm -r lint currently fails repo-wide due to pre-existing formatting issues in video-service-hub and octo-management-dashboard — this is a known, pre-existing state, not something a fresh checkout is expected to fix on its own.

Docker Desktop

This is for trying the already-built stack locally on your own machine, without setting up Node.js, pnpm, or Angular tooling — you only need Docker Desktop.

deploy/compose.yml references each service's image as ${REGISTRY}/${...IMAGE}:${IMAGE_TAG} — there is no build: key in the compose file. Running docker compose up alone does not build any images locally; it only tries to pull images that already exist somewhere. You must either build the four images yourself first, or point REGISTRY/IMAGE_TAG at a registry where they were already built and pushed.

Option A — build the images locally

The three NestJS backends build with .github/docker/node.Dockerfile; the dashboard builds with .github/docker/angular.Dockerfile. Tag each image so its name matches what compose.yml expects (${REGISTRY}/${...IMAGE}:${IMAGE_TAG}) — for a purely-local run you can set REGISTRY to something simple like local and IMAGE_TAG to dev: 

docker build -f .github/docker/node.Dockerfile \
  --build-arg RUNTIME_VERSION=24 \
  --build-arg PACKAGE_NAME=@cloudless/mqtt-puppeteer \
  --build-arg PROJECT_PATH=apps/mqtt-puppeteer \
  --build-arg BUILD_OUTPUT=dist \
  --build-arg APP_PORT=10320 \
  --build-arg START_COMMAND="node dist/main.js" \
  -t local/mqtt-puppeteer:dev .

docker build -f .github/docker/node.Dockerfile \
  --build-arg RUNTIME_VERSION=24 \
  --build-arg PACKAGE_NAME=@cloudless/ftps-remote-manager \
  --build-arg PROJECT_PATH=apps/ftps-remote-manager \
  --build-arg BUILD_OUTPUT=dist \
  --build-arg APP_PORT=10321 \
  --build-arg START_COMMAND="node dist/main.js" \
  -t local/ftps-remote-manager:dev .

docker build -f .github/docker/node.Dockerfile \
  --build-arg RUNTIME_VERSION=24 \
  --build-arg PACKAGE_NAME=@cloudless/video-service-hub \
  --build-arg PROJECT_PATH=apps/video-service-hub \
  --build-arg BUILD_OUTPUT=dist \
  --build-arg APP_PORT=10322 \
  --build-arg START_COMMAND="node dist/main.js" \
  -t local/video-service-hub:dev .

docker build -f .github/docker/angular.Dockerfile \
  --build-arg PACKAGE_NAME=@cloudless/octo-management-dashboard \
  --build-arg PROJECT_PATH=apps/octo-management-dashboard \
  --build-arg BUILD_OUTPUT=apps/octo-management-dashboard/dist/octo-management-dashboard/browser \
  --build-arg SERVER_CONFIG=apps/octo-management-dashboard/nginx.conf \
  --build-arg APP_PORT=10300 \
  -t local/octo-management-dashboard:dev .

Then export matching values so compose.yml resolves to the images you just built: 

export REGISTRY=local
export IMAGE_TAG=dev
export MQTT_PUPPETEER_IMAGE=mqtt-puppeteer
export FTPS_REMOTE_MANAGER_IMAGE=ftps-remote-manager
export VIDEO_SERVICE_HUB_IMAGE=video-service-hub
export OCTO_MANAGEMENT_DASHBOARD_IMAGE=octo-management-dashboard

Option B — point at already-built images

If images were already built and pushed elsewhere (e.g. by this repo's CI pipeline, to a registry you have pull access to), set REGISTRY and IMAGE_TAG to that registry and the commit SHA/tag you want, and skip building anything yourself.

Bring the stack up

Once the images exist under the names compose.yml expects, copy .env.example to configure the printer and camera variables that compose.yml reads (plus the per-service *_HOST_PORT / *_CONTAINER_PORT variables it needs — see .env.example), then: 

docker compose -f deploy/compose.yml up -d

Open the dashboard at http://localhost:10300.

Ports

ServicePortPurpose
mqtt-puppeteer10320REST API + health
ftps-remote-manager10321REST API
video-service-hub10322REST API + MJPEG streaming + health
video-service-hub1883Embedded MQTT broker (published separately from the app port)
octo-management-dashboard10300Web UI (served via nginx)

ftps-remote-manager has no /health endpoint yet, so the dashboard's depends_on entry for it uses the service_started condition rather than service_healthy. In practice this means Compose only waits for that container to start, not for it to actually be ready to serve requests — mqtt-puppeteer and video-service-hub do get real healthchecks (/api/mqtt/health, /health) and the dashboard waits for those to pass before it starts.

Local server

This is essentially the same procedure as Docker Desktop above, but framed for a dedicated, always-on host on your LAN — a NAS, a mini-PC, a Raspberry Pi-class box, or similar — rather than your own development machine, so the dashboard and printer bridge stay reachable even when your laptop is off.

Steps

  • Build or pull the four images once on (or for) that host, exactly as described in the Docker Desktop section above.
  • Configure .env with the printer/camera variables on that host.
  • Run docker compose -f deploy/compose.yml up -d on that host.

Every service in deploy/compose.yml already sets restart: unless-stopped. Combined with Docker's own daemon being configured to start on boot (the default on most NAS/Docker Desktop-on-boot setups), this means the whole stack comes back up automatically after the host reboots — no manual docker compose up needed after a power cycle.

Instead of opening http://localhost:10300, point your browser at that machine's LAN IP, e.g. http://<server-lan-ip>:10300, from any device on the same network.

As an illustration of what a fixed-address local server deployment looks like, this repo's own CI/CD pipeline documents (in docs/operations.md) a production deploy target at host 192.168.1.160 pulling images from a local registry at 192.168.1.162:5000. These are just this project's own example coordinates, not addresses you should use — substitute your own server's LAN IP and, if you run one, your own image registry.

Opcje instalacji

Istnieją trzy sposoby uruchomienia całego stosu ( octo-management-dashboard wraz z trzema usługami backendowymi — mqtt-puppeteer, ftps-remote-manager i video-service-hub), w rosnącej kolejności trwałości:

  • Środowisko deweloperskie — do wprowadzania zmian w kodzie; każda usługa działa ze źródeł z automatycznym przeładowaniem.
  • Docker Desktop — do wypróbowania zbudowanego stosu lokalnie, na własnym komputerze, bez narzędzi deweloperskich Node/Angular.
  • Serwer lokalny — do trwałej, stale działającej instalacji na maszynie w sieci LAN, dostępnej dla całego gospodarstwa domowego/sieci.

Proxy serwera deweloperskiego

Serwer deweloperski Angulara dla dashboardu (ng serve, port 10300) przekazuje wywołania API do trzech usług backendowych poprzez apps/octo-management-dashboard/proxy.conf.json:

Prefiks ścieżkiPrzekierowuje do
/api/mqtthttp://localhost:10320 (mqtt-puppeteer)
/api/ftpshttp://localhost:10321 (ftps-remote-manager)
/api/videohttp://localhost:10322 (video-service-hub)

Cel proxy dla video-service-hub jest zapisany na sztywno jako port 10322 w pliku proxy.conf.json. Uruchomienie tej usługi na innym porcie psuje proxy deweloperskie dashboardu dla /api/video, chyba że dodatkowo zmienisz proxy.conf.json — serwer deweloperski nie wykrywa automatycznie innego portu. Dlatego właśnie domyślne polecenie pnpm --filter @cloudless/video-service-hub start:dev (a nie wariant z niestandardowym portem) jest tym, którego należy używać.

Docker Desktop

To sposób na wypróbowanie już zbudowanego stosu lokalnie, na własnym komputerze, bez konfigurowania Node.js, pnpm czy narzędzi Angulara — potrzebny jest tylko Docker Desktop.

deploy/compose.yml odwołuje się do obrazu każdej usługi jako ${REGISTRY}/${...IMAGE}:${IMAGE_TAG} — w pliku compose nie ma klucza build:. Samo uruchomienie docker compose up nie buduje żadnych obrazów lokalnie — próbuje jedynie pobrać obrazy, które już gdzieś istnieją. Musisz albo zbudować cztery obrazy samodzielnie, albo ustawić REGISTRY/IMAGE_TAG tak, by wskazywały na rejestr, w którym zostały już zbudowane i wypchnięte.

Opcja B — wskaż już zbudowane obrazy

Jeśli obrazy zostały już zbudowane i wypchnięte gdzie indziej (np. przez potok CI tego repozytorium, do rejestru, do którego masz dostęp), ustaw REGISTRY i IMAGE_TAG na ten rejestr oraz żądany SHA/tag commita i pomiń samodzielne budowanie.

Uruchomienie stosu

Gdy obrazy istnieją pod nazwami oczekiwanymi przez compose.yml, skopiuj .env.example, aby skonfigurować zmienne drukarki i kamery odczytywane przez compose.yml (a także zmienne *_HOST_PORT/*_CONTAINER_PORT dla każdej usługi — zob. .env.example), a następnie: 

docker compose -f deploy/compose.yml up -d

Otwórz dashboard pod adresem http://localhost:10300.

Serwer lokalny

Jest to zasadniczo ta sama procedura co w przypadku Docker Desktop powyżej, ale ujęta z myślą o dedykowanym, stale działającym hoście w sieci LAN — NAS-ie, mini-PC, urządzeniu klasy Raspberry Pi lub podobnym — a nie o Twoim komputerze deweloperskim, tak aby dashboard i most drukarki pozostawały dostępne nawet wtedy, gdy Twój laptop jest wyłączony.

Kroki

  • Zbuduj lub pobierz cztery obrazy jednorazowo na (lub dla) tym hoście, dokładnie tak jak opisano w sekcji Docker Desktop powyżej.
  • Skonfiguruj .env ze zmiennymi drukarki/kamery na tym hoście.
  • Uruchom docker compose -f deploy/compose.yml up -d na tym hoście.

Każda usługa w deploy/compose.yml ma już ustawione restart: unless-stopped. W połączeniu z demonem Dockera skonfigurowanym do uruchamiania się przy starcie systemu (domyślne w większości konfiguracji NAS/Docker Desktop uruchamianych przy starcie), oznacza to, że cały stos wraca automatycznie po ponownym uruchomieniu hosta — bez potrzeby ręcznego docker compose up po cyklu zasilania.

Zamiast otwierać http://localhost:10300, skieruj przeglądarkę na adres IP tej maszyny w sieci LAN, np. http://<adres-ip-serwera>:10300, z dowolnego urządzenia w tej samej sieci.

Jako ilustrację tego, jak wygląda wdrożenie na stałym adresie lokalnego serwera, dokumentacja potoku CI/CD tego repozytorium (w docs/operations.md) opisuje docelowy host produkcyjny 192.168.1.160, pobierający obrazy z lokalnego rejestru pod adresem 192.168.1.162:5000. Są to jedynie przykładowe współrzędne tego konkretnego projektu, a nie adresy, których należy używać — podstaw adres IP własnego serwera w sieci LAN oraz, jeśli taki prowadzisz, własny rejestr obrazów.
